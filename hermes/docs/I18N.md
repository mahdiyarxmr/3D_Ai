# Localization

## The convention

One convention, chosen and applied everywhere: **per-language directories with
namespaced files.**

```
locales/
├── en/{common,settings,voice,permissions}.json
├── ja/{common,settings,voice,permissions}.json
└── fa/{common,settings,voice,permissions}.json
```

Earlier drafts of this repo mixed flat `en.json` with `fa/common.json`. That is
resolved: the layout above is the only supported one.

### Namespaces

| Namespace     | Contains                                                     |
| ------------- | ------------------------------------------------------------ |
| `common`      | App-wide chrome: actions, modes, chat, status, errors, tray   |
| `settings`    | The settings screen and everything it configures              |
| `voice`       | Voice controls and voice parameter labels/descriptions        |
| `permissions` | Levels, risk classes, confirmation dialogs, audit vocabulary  |

### Keys

Nested objects, addressed by dot path, optionally namespace-prefixed:

```ts
t('app.name')                     // defaults to the `common` namespace
t('permissions:levels.OBSERVE.title')
t('settings:language.ui')
```

Key names describe **meaning**, never appearance. `actions.save`, not
`blueButtonTopRight`.

### Interpolation

`{{placeholder}}`, substituted at render time:

```json
{ "confirm": { "body": "Allow {{character}} to run {{tool}}?" } }
```

Never assemble a sentence from fragments. Word order differs across English,
Japanese and Persian, and concatenation makes correct translation impossible.
`tests/ui.test.tsx` asserts that the permission prompt interpolates rather than
concatenates.

### Fallback

Requested language → `en` → the key itself. A missing key renders visibly as
its key rather than as an empty space, so it is caught in review instead of
shipping blank.

## Runtime switching

`I18nProvider` holds all loaded bundles in memory and swaps the active language
with no reload and no loss of state. On every change it sets three attributes
on `<html>`:

| Attribute   | Value              | Purpose                               |
| ----------- | ------------------ | ------------------------------------- |
| `lang`      | `en` / `ja` / `fa` | Accessibility, hyphenation            |
| `dir`       | `ltr` / `rtl`      | The single source of direction        |
| `data-lang` | same as `lang`     | CSS hook for per-language font stacks |

Fonts: Vazirmatn for Persian, Noto Sans JP for Japanese, Inter for Latin,
selected by `html[data-lang="…"]`.

## RTL

Persian is right-to-left, and this is handled structurally rather than with
per-component overrides.

1. **Direction is set once**, on `<html dir>`. No component sets its own.
2. **CSS logical properties only** — `margin-inline-start`, `padding-inline`,
   `inset-inline-end`, `text-align: start`. There is no `left`/`right` in the
   layout CSS, so the entire UI mirrors automatically.
3. **Icons that encode direction** (back, next, send) are flipped with
   `[dir='rtl'] .icon-directional { transform: scaleX(-1); }`. Icons that do
   not — save, settings, microphone — are left alone.
4. **Inherently LTR content inside RTL text** is wrapped in `<Bidi>`, which
   emits `dir="ltr"` plus `unicode-bidi: isolate`. Use it for file paths,
   commands, URLs, tool identifiers and code. Without it, `C:\Users\dev` inside
   a Persian sentence renders scrambled.
5. **Numerals** go through `Intl.NumberFormat`/`DateTimeFormat` for the active
   language.

`tests/ui.test.tsx` renders the real provider in jsdom and asserts `dir` flips
to `rtl` for Persian and back again for English.

## UI language ≠ conversation language

Two independent settings, by design.

| Setting                | Controls                                        |
| ---------------------- | ----------------------------------------------- |
| `language.ui`          | Buttons, labels, dialogs, tray                  |
| `language.conversation`| What the agent speaks and writes; TTS selection |

A Persian-speaking user can run the interface in Persian while conversing in
Japanese. The conversation language is passed to the LLM provider and to TTS;
it never touches the UI bundle.

## Adding a language

1. `mkdir locales/xx` and copy the four English files.
2. Translate the values. Leave the keys untouched.
3. Add the code to `SUPPORTED_LANGUAGES` in `packages/shared/src/index.ts`, and
   to `RTL_LANGUAGES` if it is right-to-left.
4. Register the bundle in `apps/desktop/src/locales.ts`.
5. Run `npm test`. The parity suite fails on any missing or extra key, on
   placeholder mismatches, and on empty strings.

## What the parity tests enforce

`tests/locales.test.ts` (44 tests):

- every language has all four namespace files;
- key sets are **identical** across languages — missing *and* extra both fail;
- no empty or whitespace-only values;
- `{{placeholders}}` match English exactly, per key;
- structure matches — a key that is an object in one language cannot be a
  string in another;
- no unescaped `{single}` braces, a common typo for `{{double}}`;
- Persian files actually contain Perso-Arabic script, and Japanese files
  contain kana or kanji (catches untranslated copy-paste);
- the `NAMESPACES` constant matches what is on disk.
